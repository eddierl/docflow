# CI: How the `test` Job Works

`.github/workflows/ci.yml` runs two jobs: **Quality Checks** (lint + typecheck) and **Unit Tests** (the full `test` job, which includes the E2E suite). This page documents the second, which spins up the whole system the same way you would locally — with one difference: the **document worker runs as an ECS task emulated by Floci**, not as a local `tsx` process.

## Why run the worker on ECS in CI?

Locally, the worker is documented to run either on the machine or in an ECS container (`pnpm dev:local` / `pnpm dev:docker`). CI takes the container path so the e2e run exercises the same deployment shape as `dev:docker` — the worker's environment, image, and ECS service all come from `terraform/ecs.tf` and `Dockerfile.worker` instead of a second, hand-maintained startup path.

## The flow, step by step

1. **Configure Docker for the Floci registry** — Floci's registry speaks plain HTTP on `127.0.0.1:5100`, so the step *merges* `127.0.0.1:5100` and `000000000000.dkr.ecr.us-east-1.localhost:5100` into the runner's `/etc/docker/daemon.json` `insecure-registries` (merging, not replacing, so runner defaults like `add-host` survive), maps the `*.localhost` ECR hostname to `127.0.0.1` in `/etc/hosts` (glibc doesn't resolve `*.localhost`), restarts the Docker daemon, and brings the job's service containers (Postgres) back up.
2. **Start Floci** — one container publishing only `4566` (the AWS API), with the Docker socket mounted and `FLOCI_DEFAULT_REGION=us-east-1`. The image is **pinned by digest** (not `:latest`): `:latest` drifts, and newer builds run ECR as a separate backing container (`floci-ecr-registry`) that binds the host's `0.0.0.0:5100` itself. Publishing `5100` on the floci container conflicts with that container ("port is already allocated"), which silently kills ECR — so the floci container publishes only `4566`, and the registry (bound on the host) is still reachable at `127.0.0.1:5100`.
3. **Wait for Floci** — polls `/_health` on `4566` only, using bare `curl` *without* `-f`: the endpoint is proxied to S3 and 404s until buckets exist, so any HTTP response proves the API is up. The registry is deliberately *not* checked here — at this point it does not exist yet (see step 4).
4. **Provision ECR repository** — `terraform apply -target=aws_ecr_repository.worker`, then exports the repo URL and a per-run image tag (`e2e-<run id>-<attempt>`; a unique tag sidesteps Floci's digest pinning of `:latest`) to `$GITHUB_ENV`. Side effect: `CreateRepository` is the first ECR operation, which makes Floci **lazily spawn** its backing registry container bound to the host's port `5100`.
5. **Wait for Floci registry** — polls `127.0.0.1:5100/v2/` (30 × 2s). This gates the whole push/deploy path on the registry that step 4 just triggered, so a registry failure fails the run here in about a minute (printing `docker ps -a` + the last 50 lines of `docker logs floci`) instead of surfacing hours later as endless terraform/docker retries.
6. **Build & push worker image** — `docker build -f Dockerfile.worker` tagged two ways: `127.0.0.1:5100/docflow-worker:<tag>` (for `docker push`) and the exact `repository_url` from Terraform (so the task definition's image name matches the local image store if Floci resolves images from there). Then `aws ecr get-login-password` + `docker login` + push.
7. **Provision local infra** — full `terraform apply` against Floci (queues, DLQ, ECR, ECS task definition + `docflow-worker` service on the `docflow` cluster). `TF_VAR_worker_image_tag` is the per-run tag; `TF_VAR_worker_database_name=docflow-test` matches the job's Postgres service.
8. **Detect worker host address** — the task container must reach the runner's published ports (Postgres 5432, Floci 4566). Floci may place the container in different network modes, so the step finds the worker container, inspects its `NetworkMode`, probes `host.docker.internal` from that network with an `alpine` one-shot, and falls back to `localhost` (host mode) or the network gateway (bridge).
9. **Re-apply worker with detected host** *(only if the detected host differs from the task definition's `host.docker.internal` default)* — updates the task definition + service and does the Floci digest-pin workaround: `desired-count 0` → wait → `1` → wait, the same restart `pnpm worker:docker:deploy` performs locally.
10. **Run database migrations, start services, run tests** — API and outbox-worker start locally (`tsx`), the document worker is expected to already be running as the ECS task. The step hard-gates on `aws ecs describe-services ... runningCount == 1` (failing the run with `docker ps -a` + `docker logs floci` on timeout) and does a *non-gating* best-effort curl of the worker's `:3001` port, since Floci may not publish task ports to the host.

## Failure diagnostics

If the worker task never reaches `running`, the failing step prints `docker ps -a` and the last 50 lines of `docker logs floci`. Useful things to look for there: image pull errors (registry/TLS), crash-looping task containers, which network the task was created on, and `Failed to start ECR backing registry container` / `Failed to adopt existing ECR registry container` lines (registry container issues, see the [registry container quirk](../README.md#floci-quirks-to-know-about)).

## Things that are intentional, not bugs

- **`docflow-test` as the worker database name** in CI: the task definition uses `${var.worker_database_name}` so CI can point the containerized worker at the job's Postgres DB while local dev keeps the `docflow` default in `terraform/variables.tf`.
- **The registry on `127.0.0.1:5100` + insecure registries**: Floci's registry is plain HTTP and runs as the separate `floci-ecr-registry` backing container bound to the host's port `5100` — which is why neither the CI `docker run` nor `docker-compose.yml` publishes `5100` on the floci container itself. Local dev pushes to the same address via the same flow (see the [registry quirk](../README.md#floci-quirks-to-know-about)).
- **No teardown steps**: nothing removes Floci, the Terraform state, or the images after the run. GitHub-hosted runners are ephemeral, so the whole environment dies with the runner; there is no long-lived state to clean up.
